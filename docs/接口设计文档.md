## 一、通用约定

### 1.1 统一响应体结构

```json
{
  "code": 200,
  "msg": "success",
  "data": {}
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `code` | int | 业务码：200 成功，4xxx 业务异常，5xxx 系统异常 |
| `msg` | string | 提示信息。成功时返回简洁文案（如"登录成功""签到成功"），查询类请求返回 "success"；失败时返回具体错误描述，前端可直接展示给用户 |
| `data` | object/null | 响应数据，成功时携带，失败时为 null |

### 1.2 通用业务码一览

| code | 含义 | 说明 |
|------|------|------|
| 200 | 成功 | 请求处理成功 |
| 4000 | 请求参数错误 | 参数缺失或格式不合法 |
| 4001 | 认证失败 | 未登录或 token 无效 |
| 4002 | 权限不足 | 当前角色无权操作 |
| 4003 | 资源不存在 | 请求的资源不存在 |
| 4004 | 资源冲突 | 重复操作等（如重复抢票） |
| 4100 | 业务逻辑错误 | 通用的业务失败（如活动已下线） |
| 4101~4107 | 签到专用业务码 | 详见签到接口业务码一览 |
| 5000 | 服务器内部错误 | 未预期的系统异常 |

### 1.3 安全说明

> **密码存储**：后端始终对密码进行加密哈希（如 BCrypt）后存储，绝不保存明文。
> **密码传输**：MVP 阶段暂使用明文传输密码。生产环境须启用 HTTPS，并建议前端先对密码进行加盐哈希后再传输，确保传输过程和存储环节均不出现明文密码。

### 1.4 认证方式

所有需要登录的接口在请求头中携带：

```
Authorization: Bearer <jwt_token>
```

JWT Token 中编码的用户信息：

| 字段 | 说明 |
|------|------|
| `userId` | 用户 ID |
| `username` | 用户名 |
| `role` | 角色：`attendee` / `organizer` |

### 1.5 分页请求约定

所有列表接口的分页参数：

| 参数 | 类型 | 默认值 | 最大值 | 说明 |
|------|------|--------|--------|------|
| `page` | int | 1 | - | 页码（从 1 开始） |
| `size` | int | 10 | 100 | 每页条数，超出最大值时自动截断为 100 |

### 1.6 分页响应结构

```json
{
  "code": 200,
  "msg": "success",
  "data": {
    "records": [],
    "total": 100,
    "page": 1,
    "size": 10,
    "pages": 10
  }
}
```

## 二、认证模块

### 2.1 用户注册

```
POST /api/v1/auth/register
```

**请求体**：

```json
{
  "username": "zhangsan",
  "password": "abc123456",
  "role": "attendee"
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `username` | string | 是 | 用户名，长度 2-50 字符 |
| `password` | string | 是 | 密码，长度 6-50 字符 |
| `role` | string | 是 | 角色：`attendee`（参会者）/ `organizer`（举办方） |

**成功响应**：

```json
{
  "code": 200,
  "msg": "注册成功",
  "data": {
    "token": "eyJhbGciOiJIUzI1NiIs...",
    "userId": 1,
    "username": "zhangsan",
    "role": "attendee"
  }
}
```

**说明**：注册成功后直接返回 token。前端必须根据注册时选择的 `role` 分支处理：
- `role = attendee`（普通参会者）：临时存入 token，跳转注册后偏好设置页，调用 `PUT /api/v1/user/profile` 补充 `gender/tags`，完成后清除临时登录态并回到登录页。
- `role = organizer`（活动举办方）：不得进入偏好设置页；无需补充画像，前端可清除临时登录态并回到登录页。

**错误场景**：

| code | msg | 说明 |
|------|-----|------|
| 4000 | 用户名已存在 | username 重复 |
| 4000 | 参数错误：角色只能是 attendee 或 organizer | role 枚举值不合法 |

## 三、用户模块

### 3.1 获取当前用户信息

```
GET /api/v1/user/profile
```

**请求头**：`Authorization: Bearer <token>`

**成功响应**：

```json
{
  "code": 200,
  "msg": "success",
  "data": {
    "userId": 1,
    "username": "zhangsan",
    "role": "attendee",
    "gender": "male",
    "tags": ["科技", "电竞"],
    "avatarUrl": "default.png",
    "createdAt": "2026-07-01 10:00:00"
  }
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `userId` | int | 用户 ID |
| `username` | string | 用户名 |
| `role` | string | 角色 |
| `gender` | string/null | 性别：`male` / `female` / `other`，举办方为 null |
| `tags` | string[]/null | 偏好标签数组，举办方为 null |
| `avatarUrl` | string | 头像 URL（当前固定为 default.png） |
| `createdAt` | string | 注册时间，格式 `yyyy-MM-dd HH:mm:ss` |

**注意**：返回的 `userId`、`role` 等字段应与 token 中的信息一致，
前端也可直接解析 token 获取基本信息以减少请求。

---

### 3.2 更新用户信息

```
PUT /api/v1/user/profile
```

**请求头**：`Authorization: Bearer <token>`

**请求体**：

```json
{
  "gender": "female",
  "tags": ["音乐", "学术"]
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `gender` | string | 否 | 性别：`male` / `female` / `other` |
| `tags` | string[] | 否 | 偏好标签数组 |

**约束**：
- 仅 `role = attendee` 的用户可修改，举办方调用返回 4002 权限不足。
- `gender` 和 `tags` 至少传一个，全不传返回 4000 参数错误。
- 首次注册后的偏好设置页仅面向 `role = attendee` 的普通参会者，必须同时提交 `gender` 和至少一个 `tags`；后续个人资料页可按需只修改其中一个字段。

**成功响应**：

```json
{
  "code": 200,
  "msg": "更新成功",
  "data": null
}
```

### 3.3 获取用户历史参会记录

```
GET /api/v1/user/history
```

**请求头**：`Authorization: Bearer <token>`（仅 attendee 角色）

**说明**：返回当前参会者所有历史参会记录，即该用户拥有 ticket 的活动列表（含已结束活动）。用于用户在个人中心查看自己的参会足迹。

**查询参数**：

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| `page` | int | 否 | 1 | 页码 |
| `size` | int | 否 | 10 | 每页条数（最大值 100） |

**成功响应**：

```json
{
  "code": 200,
  "msg": "success",
  "data": {
    "records": [
      {
        "eventId": 1,
        "title": "2026年校园科技展",
        "location": "人文馆主厅",
        "startTime": "2026-09-15 09:00:00",
        "endTime": "2026-09-15 17:00:00",
        "tags": ["科技", "电竞"],
        "ticketStatus": "checked",
        "checkedAt": "2026-09-15 08:30:00",
        "purchasedAt": "2026-07-05 14:30:00"
      },
      {
        "eventId": 2,
        "title": "校园音乐会",
        "location": "梅园操场",
        "startTime": "2026-09-20 19:00:00",
        "endTime": null,
        "tags": ["音乐"],
        "ticketStatus": "pending",
        "checkedAt": null,
        "purchasedAt": "2026-07-06 10:00:00"
      }
    ],
    "total": 2,
    "page": 1,
    "size": 10,
    "pages": 1
  }
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `eventId` | int | 活动 ID |
| `title` | string | 活动标题 |
| `location` | string | 活动地点 |
| `startTime` | string | 活动开始时间 |
| `endTime` | string/null | 活动结束时间 |
| `tags` | string[]/null | 活动标签数组 |
| `ticketStatus` | string | 该用户对该活动的票状态：`pending` / `checked` / `invalid` / `refunded` |
| `checkedAt` | string/null | 签到时间（已签到时有值） |
| `purchasedAt` | string | 购票时间 |

**说明**：
- 该接口按购票时间 `purchasedAt` 降序排列，最新购票的记录排最前。
- 与「我的票夹」（5.2）的区别：我的票夹侧重展示票务状态和二维码入口，用户可在票夹中对票进行操作（如查看二维码）；历史参会记录侧重展示参会经历，供用户回顾自己参与过的活动，不展示二维码操作入口。
- 后端查询逻辑：以当前用户 ID 关联 ticket 表，再 JOIN event 表获取活动详情。返回该用户所有 ticket 对应的活动信息。

**错误场景**：

| code | msg | 说明 |
|------|-----|------|
| 4001 | 认证失败 | 未登录或 token 无效 |
| 4002 | 权限不足 | 仅参会者（attendee）可查看历史记录 |

## 四、活动模块

### 4.1 发布活动

```
POST /api/v1/event
```

**请求头**：`Authorization: Bearer <token>`（仅 organizer 角色）

**请求体**：

```json
{
  "title": "2026年校园科技展",
  "description": "这是一场展示最新科技成果的盛会...",
  "location": "人文馆主厅",
  "tags": ["科技", "电竞"],
  "startTime": "2026-09-15 09:00:00",
  "endTime": "2026-09-15 17:00:00",
  "totalTickets": 200
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `title` | string | 是 | 活动标题，1-100 字符 |
| `description` | string | 否 | 活动描述，可为空或由 AI 生成填充 |
| `location` | string | 否 | 活动地点纯文本，如"人文馆主厅" |
| `tags` | string[] | 否 | 活动标签数组，如 `["科技","电竞"]`，用于推荐系统双向标签匹配。传 NULL 或空数组表示无标签 |
| `startTime` | string | 是 | 开始时间，格式 `yyyy-MM-dd HH:mm:ss`，必须晚于当前时间 |
| `endTime` | string | 否 | **结束时间**，格式 `yyyy-MM-dd HH:mm:ss`，可选。传入时必须晚于 `startTime` |
| `totalTickets` | int | 是 | 门票总数，必须是 1~99999 之间的整数 |

**新增校验**：
- `endTime` 不为空时，必须晚于 `startTime`，否则返回 4000（结束时间不能早于开始时间）。
- `endTime` 可为空（表示该活动无固定结束时间，不会自动变为 finished）。
- `tags` 为 JSON 字符串数组，每个标签长度不超过 20 字符，总字符串长度不超过 255 字符。

**成功响应**：

```json
{
  "code": 200,
  "msg": "发布成功",
  "data": {
    "eventId": 1,
    "status": "draft"
  }
}
```

**说明**：新发布的活动默认状态为 `draft`（草稿），需举办方手动上线。

### 4.2 获取活动列表

```
GET /api/v1/event/list
```

**请求头**：
- `scope=public`：无需携带 `Authorization` 头（公开接口）。
- `scope=organizer`：需携带 `Authorization: Bearer <token>`（仅 organizer 角色）。

**查询参数**：

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| `scope` | string | 否 | `public` | 列表范围：`public`（公开，仅 online）/ `organizer`（举办方自己的所有活动） |
| `page` | int | 否 | 1 | 页码 |
| `size` | int | 否 | 10 | 每页条数（最大值 100） |

**scope 行为说明**：
- `scope=public`（或默认）：返回所有 `status=online` 的活动，**无需登录**，用于 C端活动大厅。
- `scope=organizer`：返回当前登录用户（必须是 organizer）发布的所有活动（含 draft / online / offline / finished），用于 B端活动管理列表。

**C端公开列表响应**：

```json
{
  "code": 200,
  "msg": "success",
  "data": {
    "records": [
      {
        "eventId": 1,
        "title": "2026年校园科技展",
        "description": "这是一场展示最新科技成果的盛会...",
        "location": "人文馆主厅",
        "tags": ["科技", "电竞"],
        "startTime": "2026-09-15 09:00:00",
        "endTime": "2026-09-15 17:00:00",
        "totalTickets": 200,
        "soldTickets": 120,
        "status": "online",
        "createdAt": "2026-07-01 10:00:00"
      }
    ],
    "total": 1,
    "page": 1,
    "size": 10,
    "pages": 1
  }
}
```

**B端举办方列表响应**（比公开列表多 `updatedAt` 时间戳）：

```json
{
  "code": 200,
  "msg": "success",
  "data": {
    "records": [
      {
        "eventId": 1,
        "title": "2026年校园科技展",
        "description": "这是一场展示最新科技成果的盛会...",
        "location": "人文馆主厅",
        "tags": ["科技", "电竞"],
        "startTime": "2026-09-15 09:00:00",
        "endTime": "2026-09-15 17:00:00",
        "totalTickets": 200,
        "soldTickets": 120,
        "status": "online",
        "createdAt": "2026-07-01 10:00:00",
        "updatedAt": "2026-07-02 14:00:00"
      }
    ],
    "total": 1,
    "page": 1,
    "size": 10,
    "pages": 1
  }
}
```

**说明**：C端和B端共用此接口，通过 `scope` 参数区分，由后端根据 scope 和当前用户角色做鉴权。

### 4.4 更新活动信息

```
PUT /api/v1/event/{eventId}
```

**请求头**：`Authorization: Bearer <token>`（仅 organizer 角色，且必须是该活动的发布者）

**请求体**（全部可选，只传需要修改的字段）：

```json
{
  "title": "2026年校园科技展（更新版）",
  "description": "更新后的活动描述...",
  "location": "人文馆副厅",
  "tags": ["科技", "电竞", "创新"],
  "startTime": "2026-09-16 09:00:00",
  "endTime": "2026-09-16 18:00:00",
  "totalTickets": 300
}
```

**新增/修改的约束**：
- 活动处于 `finished` 状态时，**不允许修改任何字段**，返回 4100（活动已结束，不可修改）。
- 活动处于 `draft`、`online` 或 `offline` 状态时均允许修改 `totalTickets`，但新值**不能小于当前 `soldTickets`**，且必须在 1~99999 之间；前端页面按当前产品约束进一步限制为 1~100 的整数。
- `startTime` 如果传入过去的时间，应返回 4000 参数错误（开始时间不能早于当前时间）。
- `endTime` 如果传入，必须晚于 `startTime`（当同时修改 startTime 时，比较新值；否则比较现有 startTime），否则返回 4000（结束时间不能早于开始时间）。
- `tags` 修改规则与 `title` 相同：JSON 字符串数组，每个标签长度不超过 20 字符，总字符串长度不超过 255 字符。

**成功响应**：

```json
{
  "code": 200,
  "msg": "更新成功",
  "data": null
}
```

### 4.5 上线/下线活动

```
PATCH /api/v1/event/{eventId}/status
```

**请求头**：`Authorization: Bearer <token>`（仅 organizer 角色）

**请求体**：

```json
{
  "status": "online"
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `status` | string | 是 | 目标状态：`online`（上线）/ `offline`（下线） |

**状态流转规则**（含 finished 状态）：

| 当前状态 | 目标状态 | 是否允许 | 说明 |
|----------|----------|----------|------|
| `draft` | `online` | ✅ | 允许上线 |
| `draft` | `offline` | ❌ | 直接下线草稿无意义，需先上线 |
| `draft` | `finished` | ❌ | finished 为自动状态，不可手动设置 |
| `online` | `offline` | ✅ | 允许下线 |
| `online` | `finished` | ❌ | finished 为自动状态，不可手动设置 |
| `offline` | `online` | ✅ | 允许重新上线。需额外校验 `total_tickets >= sold_tickets`，否则返回 4100 |
| `offline` | `finished` | ❌ | finished 为自动状态，不可手动设置 |
| `finished` | 任何状态 | ❌ | 活动已结束，不可变更状态 |

**新增约束**：
- 当前状态为 `finished` 时，无论请求目标状态是什么，都返回 4100（活动已结束，不可变更状态）。
- 请求目标状态为 `finished` 时，返回 4000（finished 为自动状态，不可手动设置）。

**成功响应**：

```json
{
  "code": 200,
  "msg": "活动已上线",
  "data": null
}
```

**错误场景**：

| code | msg |
|------|-----|
| 4100 | 状态流转不合法：不能从 draft 直接变为 offline |
| 4100 | 活动已结束，不可变更状态 |
| 4000 | finished 为自动状态，不可手动设置 |
| 4100 | 门票总数不能小于已售数量，请先修改 totalTickets 后再上线 |

### 5.4 举办方扫码核销签到

```
POST /api/v1/ticket/checkin
```

**请求头**：`Authorization: Bearer <token>`（仅 organizer 角色）

**请求体**：

```json
{
  "code": "ticket_1_1_15_1718888888_1718888889"
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `code` | string | 是 | 扫码解析出的完整文本 |

**code 文本格式**（扫码场景）：
```
ticket_{eventId}_{ticketNo}_{timestamp}
```

其中 `timestamp` 为前端生成二维码时的**秒级 Unix 时间戳**。

例如：`ticket_1_1_15_1718888888_1718888889`

**手动输入兜底**（无摄像头场景）：
举办方也可在输入框中直接输入 `ticketNo`（票号，如 `1_15_1718888888`），前端将其包装为 `ticket_{ticketNo}` 格式（即 `ticket_1_15_1718888888`）传入 `code` 字段，调用同一签到接口。后端解析时兼容此格式（手动输入无 eventId 和时间戳时，跳过 eventId 校验和时间戳校验）。

**后端签到处理流程**：

```
1. 解析 code 文本：
   ├─ 先尝试匹配完整格式：^ticket_(\d+)_(.+)_(\d{10,})$
   │    成功 → 提取 eventId, ticketNo, timestamp → 执行步骤 2（含时间戳校验）
   ├─ 若失败，再尝试匹配手动输入格式：^ticket_(.+)$
   │    成功 → 提取 ticketNo → 跳过步骤 2（时间戳校验），直接进入步骤 3
   └─ 两者均失败 → 返回 4101（无效的签到凭证，格式不合法）

2. 校验时间戳（仅完整格式）：当前时间 - timestamp > 60 秒？
   ├─ 是 → 返回 4102（二维码已过期，请刷新）
   └─ 否 → 继续

3. 根据 ticketNo 查询 ticket 记录
   ├─ 不存在 → 返回 4103（票务不存在）
   └─ 存在 → 继续

3a. 校验 ticket 的 event_id 是否匹配解析出的 eventId（仅完整格式）
   ├─ 不匹配 → 返回 4101（无效的签到凭证，票务与活动不匹配）
   └─ 匹配 → 继续

3b. 校验签到者是否为该活动的举办方
   ├─ 当前登录用户 ID != ticket.event.organizer_id
   │    → 返回 4002（权限不足，您不是该活动的举办方）
   └─ 匹配 → 继续

3c. 校验活动是否已结束
   ├─ 关联活动的 status = 'finished'
   │    → 返回 4107（活动已结束，无法签到）
   └─ 其他 → 继续

4. 检查 ticket.status
   ├─ checked → 返回 4104（请勿重复签到）
   ├─ invalid → 返回 4105（票务已失效）
   ├─ refunded（预留）→ 返回 4106（票务已退票）
   └─ pending → 执行签到

5. 原子更新：
   UPDATE ticket SET status = 'checked', checked_at = NOW()
   WHERE id = ? AND status = 'pending'
   ├─ 影响行数 = 0 → 返回 4104（请勿重复签到，兜底）
   └─ 影响行数 = 1 → 签到成功
```

**成功响应**：

```json
{
  "code": 200,
  "msg": "签到成功",
  "data": {
    "ticketNo": "1_15_1718888888",
    "eventTitle": "2026年校园科技展",
    "checkedAt": "2026-07-07 10:30:00"
  }
}
```

**签到接口业务码一览**：

| code | msg | 说明 |
|------|-----|------|
| 200 | 签到成功 | 正常核销 |
| 4002 | 权限不足，您不是该活动的举办方 | 当前 organizer 不是该活动的发布者 |
| 4101 | 无效的签到凭证，格式不合法 | 外部二维码或非法文本 |
| 4102 | 二维码已过期，请刷新 | 时间戳超过 1 分钟 |
| 4103 | 票务不存在 | ticketNo 在 DB 查不到 |
| 4104 | 请勿重复签到 | ticket 已为 checked 状态 |
| 4105 | 票务已失效 | ticket 为 invalid 状态 |
| 4106 | 票务已退票 | ticket 为 refunded 状态（预留） |
| **4107** | **活动已结束，无法签到** | **关联活动为 finished 状态** |

## 九、注意事项与约束

1. **时间格式**：所有请求和响应中的时间字段统一使用 `yyyy-MM-dd HH:mm:ss` 格式。
2. **分页默认值**：前端未传分页参数时，默认 `page=1, size=10`。
3. **JWT 过期时间**：Token 过期时间暂定为 24 小时，过期后前端需引导用户重新登录。
4. **不存在的数据删除接口**：
   - 抢票（purchase）没有取消接口（与"暂不支持退票"一致）。
   - 用户注销没有接口。
5. **角色约束在接口层实现**：后端通过 JWT 中的 `role` 字段在拦截器或控制器层做权限检查，而非依赖前端传参。
6. **频率限制**：
   - 抢票接口（`POST /api/v1/ticket/purchase`）：同一用户每秒最多请求 1 次，超出返回 429（Too Many Requests）。
   - 签到接口（`POST /api/v1/ticket/checkin`）：同一举办方每秒最多请求 5 次，超出返回 429。
   - 具体限流策略可在网关层或 AOP 切面中实现，当前 MVP 阶段可暂不实现，但接口设计与前端需预留容错处理。
7. **标签格式规范**：
   - `user.tags` 和 `event.tags` 均为 JSON 字符串数组，如 `["科技","电竞"]`。
   - 每个标签长度不超过 20 字符。
   - 总 JSON 字符串长度不超过 255 字符。
   - 后端存储为 VARCHAR(255)，不做 JSON 字段类型校验，仅作字符串存读取。
8. **历史参会记录与我的票夹的区别**：
   - 「我的票夹」（5.2）：侧重票务管理，展示当前有效票和二维码操作入口，含分页和状态筛选。
   - 「历史参会记录」（3.3）：侧重参会回顾，展示用户所有购票过的活动（包括已结束），无二维码操作，按购票时间降序排列。
