# 数据库表设计文档

> 本文档为「易签活动票务与智能签到系统」的数据库表设计规范。

## 一、核心表设计

系统共设计 **3 张核心表**：`user`（用户）、`event`（活动）、`ticket`（门票）。

---

### 1.1 `user` — 用户表

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `id` | BIGINT | PRIMARY KEY, AUTO_INCREMENT | 主键 |
| `username` | VARCHAR(50) | NOT NULL, UNIQUE | 用户名 |
| `password` | VARCHAR(255) | NOT NULL | 加密后的密码 |
| `role` | ENUM('attendee','organizer') | NOT NULL | 角色：参会者 / 举办方（注册后不可改）|
| `gender` | ENUM('male','female','other') | DEFAULT NULL | 性别（举办方为 NULL，参会者可修改）|
| `tags` | VARCHAR(255) | DEFAULT NULL | 偏好标签，JSON 数组格式，如 `["科技","电竞"]` |
| `avatar_url` | VARCHAR(255) | NOT NULL DEFAULT 'default.png' | 头像 URL（暂不支持上传，使用默认值）|
| `created_at` | DATETIME | NOT NULL DEFAULT CURRENT_TIMESTAMP | 注册时间 |

**索引**：
- `idx_role` ON (`role`)

**设计说明**：
- `gender` 和 `tags` 字段对举办方（organizer）无意义，存储为 `NULL`。查询男女比例等统计时，仅统计 `role = 'attendee'` 且 `gender IS NOT NULL` 的数据。
- 性别和偏好标签仅服务于推荐算法与数据统计，为参会者专属属性。之所以不拆分独立表，是因为本项目为 12 天 MVP，单表 NULL 字段的存储成本可忽略不计，且避免了不必要的 JOIN 操作。
- 仅普通参会者注册后偏好设置页会写入 `gender` 与 `tags` 字段；活动举办方注册后不进入偏好设置页，这两个字段保持 `NULL`。该流程不改变 `role` 与 `avatar_url` 的静态化策略。
- **[MVP方案]** `tags` 使用 VARCHAR(255) 存 JSON 数组，查询和更新效率有限。后期若需按标签做复杂推荐，建议拆分为 `user_tag` 关联表（`user_id` + `tag` 联合索引），提升检索性能。
- **[MVP方案]** `avatar_url` 默认值硬编码为 `'default.png'`。后期如切换存储方式（如 OSS），可将默认值改为 NULL，由应用层控制默认头像展示。

### 1.2 `event` — 活动表

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `id` | BIGINT | PRIMARY KEY, AUTO_INCREMENT | 主键 |
| `organizer_id` | BIGINT | NOT NULL | 举办方用户 ID（逻辑关联 `user.id`）|
| `title` | VARCHAR(100) | NOT NULL | 活动标题 |
| `description` | TEXT | | 活动描述（可为空，支持 AI 生成填充）|
| `location` | VARCHAR(255) | DEFAULT NULL | 活动地点（纯文本，如"人文馆主厅"）|
| `tags` | VARCHAR(255) | DEFAULT NULL | 活动标签 JSON 数组，如 `["科技","电竞"]`（与 `user.tags` 存储格式一致，支持双向标签匹配推荐）|
| `start_time` | DATETIME | NOT NULL | 活动开始时间 |
| `end_time` | DATETIME | DEFAULT NULL | 活动结束时间（为 NULL 表示无固定结束时间，不会自动变为 finished）|
| `total_tickets` | INT | NOT NULL DEFAULT 0 | 门票总数 |
| `sold_tickets` | INT | NOT NULL DEFAULT 0 | 已售门票数 |
| `status` | ENUM('draft','online','offline','finished') | NOT NULL DEFAULT 'draft' | 状态：草稿 / 上线 / 下线 / 已结束 |
| `created_at` | DATETIME | NOT NULL DEFAULT CURRENT_TIMESTAMP | 发布时间 |
| `updated_at` | DATETIME | NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP | 最近更新时间 |

**索引**：
- `idx_organizer` ON (`organizer_id`)
- `idx_status` ON (`status`)
- `idx_start_time` ON (`start_time`) — 活动列表按时间排序为高频查询
- `idx_end_time` ON (`end_time`) — 定时任务扫描结束时间

**状态流转规则**：

| 当前状态 | 目标状态 | 是否允许 | 触发方式 | 说明 |
|----------|----------|----------|----------|------|
| `draft` | `online` | ✅ | 手动 | 草稿上线 |
| `draft` | `offline` | ❌ | — | 直接下线草稿无意义，需先上线 |
| `draft` | `finished` | ❌ | — | 草稿不可能结束 |
| `online` | `offline` | ✅ | 手动 | 上线活动下线 |
| `online` | `finished` | ✅ | **自动** | 到达 `end_time` 时由定时任务触发 |
| `offline` | `online` | ✅ | 手动 | 重新上线，需额外校验 `total_tickets >= sold_tickets` |
| `offline` | `finished` | ✅ | **自动** | 到达 `end_time` 时由定时任务触发 |
| `finished` | 任何状态 | ❌ | — | **终态，不可逆转** |

```
draft ──✅──▶ online ──✅──▶ offline ──✅──▶ finished（自动到达 end_time）
                    ◀──✅──       ▲
                                  │
                                  └── 到达 end_time ──┘
draft ──❌──▶ offline
draft ──❌──▶ finished
finished ──❌──▶ 任何状态
```

**设计说明**：
- `location` 字段虽然文档中说明"地图定位暂不考虑"，但活动发布时需要填写地点信息，故保留纯文本字段。
- `tags` 与 `user.tags` 存储格式一致，使用 VARCHAR(255) 存 JSON 数组，便于推荐系统实现双向标签匹配。推荐接口可根据用户标签和活动标签的匹配度生成推荐理由。后期可按需拆分为 `event_tag` 关联表。
- `sold_tickets` 用于防超卖并发控制：每次抢票通过 `UPDATE event SET sold_tickets = sold_tickets + 1 WHERE id = ? AND sold_tickets < total_tickets` 实现原子扣减。
- **sold_tickets 约束**：应用层需保证 `sold_tickets ≤ total_tickets`。当 `total_tickets` 被修改时，新值不得小于当前 `sold_tickets`，否则返回业务错误。
- `updated_at` 用于记录活动上下线等状态变更时间。
- **`finished` 为终态**：活动一旦进入 `finished`，不可回退到 `online` 或 `offline`。举办方无法修改已结束活动，用户端无法核销或生成二维码。
- **自动结束机制**：由后端定时任务（`@Scheduled`，每分钟扫描）检测：`end_time IS NOT NULL AND end_time <= NOW() AND status IN ('online','offline')`，自动将状态更新为 `finished`。

### 1.3 `ticket` — 门票表

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `id` | BIGINT | PRIMARY KEY, AUTO_INCREMENT | 主键 |
| `event_id` | BIGINT | NOT NULL | 关联活动 ID（逻辑关联 `event.id`）|
| `user_id` | BIGINT | NOT NULL | 票主用户 ID（逻辑关联 `user.id`）|
| `ticket_no` | VARCHAR(64) | NOT NULL, UNIQUE | 票号，全局唯一 |
| `status` | ENUM('pending','checked','invalid','refunded') | NOT NULL DEFAULT 'pending' | 状态：待签到 / 已签到 / 已失效 / 已退票 |
| `created_at` | DATETIME | NOT NULL DEFAULT CURRENT_TIMESTAMP | 购票时间 |
| `checked_at` | DATETIME | DEFAULT NULL | 核销时间（签到成功时记录）|

**索引**：
- `uk_event_user` UNIQUE (`event_id`, `user_id`) — 一人一票唯一约束，防止同一用户重复购票
- `idx_event` ON (`event_id`)
- `idx_user` ON (`user_id`)
- `idx_status` ON (`status`)

**票号生成规则**：
```
ticket_no = ${eventId}_${userId}_${timestamp}
```
例如：`3_15_1718888888`

规则说明：
- 使用下划线拼接三个信息，确保全局唯一。
- 可从票号反解出活动 ID、用户 ID 和时间戳，便于日志排查和作弊分析。
- 生成时机：购票成功时由后端生成。

**设计说明**：
- 当前采用 **一人一票** 设计：一个用户对同一场活动只能购买一张票。后端在抢票时检查 `user_id + event_id` 是否已存在 ticket 记录。
- `status` 枚举中预置了 `'refunded'` 状态，虽然目前暂不支持退票，但预留后未来加退票逻辑时无需改表结构。
- `checked_at` 在核销签到成功时写入时间戳，用于记录签到时间。

## 二、ER 关系图（文字描述）

```
user (1) ──────< (N) ticket (N) >────── (1) event
  │                                            │
  └── 作为举办方 ──> event.organizer_id        │
                                                │
  user.id <──逻辑关联── ticket.user_id          │
  event.id <──逻辑关联── ticket.event_id        │
  user.id <──逻辑关联── event.organizer_id ─────┘
```

关系总结：
1. **user → ticket**：一对多。一个用户可拥有多张票（分属不同活动）。
2. **event → ticket**：一对多。一个活动可有多张售出门票。
3. **user → event**：一对多。一个举办方可发布多个活动。
4. **user 与 event** 之间的两种关系：user 既可以是票主（通过 ticket 关联），也可以是举办方（通过 event.organizer_id 关联），由 `user.role` 字段区分。

## 三、字段设计详细讨论

### 3.1 为什么举办方的 gender 和 tags 直接存 NULL 而不是拆分表？

**选择方案：单表 + NULL 字段**

对比过两种方案：

| 方案 | 优点 | 缺点 |
|------|------|------|
| **A：单表 + NULL**（选用） | 结构简单，无 JOIN，开发快 | 举办方字段语义上"用不到" |
| **B：垂直拆分**（user 基础表 + attendee_profile 拓展表） | 语义清晰，举办方完全不存无关字段 | 多一张表，查询需 JOIN，增加复杂度 |

**选用方案 A 的理由**：
- 本项目是 12 天 MVP 敏捷开发，简单性优先。
- NULL 在 MySQL 中存储开销极低（约 1 bit），可以忽略。
- 举办方数量通常远少于参会者，数据分析时排除 `role = 'organizer'` 即可。
- 一行数据存放所有信息，便于后期给举办方也可能加上个性化设置。

### 3.2 ticket_no 票号为什么不用自增 ID 或 UUID？

- **自增 ID**：暴露了系统总量信息，且跨表关联时不够直观。
- **UUID**：太长（36 字符），影响索引性能和存储空间。
- **本方案**：`eventId_userId_timestamp` 格式，长度可控（约 20-30 字符），且包含了完整上下文，方便排查问题。

## 四、未来可扩展性分析

以下逐条对照文档中"暂不考虑"的功能，分析当前表设计的兼容性：

### 4.1 用户头像上传
- **当前**：`user.avatar_url` 存固定值 `'default.png'`。
- **扩展**：后期接入文件服务器（如 MinIO、OSS）后，将 URL 存入该字段即可。
- **改表**：不需要。✅

### 4.2 活动宣传图
- **当前**：event 表无图片字段。
- **扩展**：后期新增 `event.poster_url` 字段，或新建 `event_image` 子表支持多图。
- **改表**：仅需新增字段。✅

### 4.3 票务支付逻辑
- **当前**：所有票免费，无金额相关字段。
- **扩展**：后期可在 ticket 表新增 `price DECIMAL(10,2)`、`payment_status ENUM('unpaid','paid','refunded')` 等字段。
- **改表**：仅需新增字段。✅

### 4.4 无票候补逻辑
- **当前**：售罄直接返回失败。
- **扩展**：后期新建 `waitlist` 表（含 `event_id`, `user_id`, `created_at`, `status`），有人退票时按候补顺序自动分配。
- **改表**：需新建表，不影响现有表。✅

### 4.5 退票逻辑
- **当前**：暂不支持退票。但 `ticket.status` 已预置 `'refunded'` 枚举值。
- **扩展**：后期实现退票接口时，将 status 改为 `'refunded'`，同时 `event.sold_tickets--`。
- **改表**：不需要，枚举值已预留。✅

### 4.6 核销时间合理性判定（活动结束时间）
- **当前**：event 表新增 `end_time` 字段，`status` 枚举增加 `'finished'`。定时任务自动将到达结束时间的活动置为 `finished`，应用层在核销、购票、修改等接口中增加对 `finished` 状态的拦截。
- **改表**：已完成，无需进一步改动。✅

### 4.7 富文本编辑器 & 地图定位
- **富文本**：`event.description` 字段类型为 TEXT，可直接存储 HTML 内容。
- **地图定位**：后期新增 `event.location_lat DECIMAL(10,7)`、`event.location_lng DECIMAL(10,7)` 字段。
- **改表**：仅需新增字段。✅

### 4.8 一人多票（帮买）
- **当前**：一人一票设计（`user_id + event_id` 唯一约束）。
- **扩展**：如果要支持一人买多张票，需要引入 `order`（订单）表作为中间层，将 ticket 改为与 order 关联而非直接与 user 关联。此改动较大，属于业务模式变更。
- **改表**：**需要较大重构**。建议在 MVP 阶段保持一人一票，如确需此功能应在项目规划阶段确认。⚠️

### 4.9 数据归档与分表
- **当前**：所有数据在同一张表。
- **扩展**：当 ticket 表数据量过大时（如百万级），可按 `event_id` 做水平分表，或按时间做归档表。
- **改表**：**需要架构改造**，但表结构本身无需变动，仅需调整 Mapper 层。⚠️

## 五、字段类型选用原则

| 类型 | 选用场景 | 示例 |
|------|----------|------|
| `BIGINT` | 主键、所有 ID 字段 | `id`, `user_id`, `event_id` |
| `VARCHAR(50)` | 短文本标识 | `username` |
| `VARCHAR(64)` | 唯一编码 | `ticket_no` |
| `VARCHAR(255)` | 短文本内容 | `tags`, `location`, `avatar_url` |
| `TEXT` | 长文本内容 | `description` |
| `ENUM` | 固定枚举值 | `role`, `status` |
| `INT` | 数量计数 | `total_tickets`, `sold_tickets` |
| `DATETIME` | 时间记录 | `created_at`, `checked_at`, `start_time`, `end_time` |

**不使用 INT 存时间戳的理由**：DATETIME 可读性强，MySQL 内部有优化，且 MyBatis-Plus 可直接映射为 `LocalDateTime`，开发体验更佳。

## 六、SQL 建表语句（完整版）

```sql
-- ============================================
-- 表1: user — 用户
-- ============================================
CREATE TABLE `user` (
  `id`          BIGINT                                       PRIMARY KEY AUTO_INCREMENT  COMMENT '主键',
  `username`    VARCHAR(50)                                  NOT NULL UNIQUE             COMMENT '用户名',
  `password`    VARCHAR(255)                                 NOT NULL                    COMMENT '加密后的密码',
  `role`        ENUM('attendee', 'organizer')                NOT NULL                    COMMENT '角色：参会者/举办方（注册后不可改）',
  `gender`      ENUM('male', 'female', 'other')              DEFAULT NULL                COMMENT '性别（举办方为NULL，参会者可修改）',
  `tags`        VARCHAR(255)                                 DEFAULT NULL                COMMENT '偏好标签JSON数组，有且仅有["文艺演出","体育赛事","学术讲座","文化活动","社团活动","心理健康"]'
  `avatar_url`  VARCHAR(255)                                 NOT NULL DEFAULT 'default.png' COMMENT '头像URL（暂不支持上传，使用默认值）',
  `created_at`  DATETIME                                     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '注册时间',
  INDEX `idx_role` (`role`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户表';


-- ============================================
-- 表2: event — 活动（含 end_time、finished 状态、tags 标签）
-- ============================================
CREATE TABLE `event` (
  `id`            BIGINT                                     PRIMARY KEY AUTO_INCREMENT  COMMENT '主键',
  `organizer_id`  BIGINT                                     NOT NULL                    COMMENT '举办方用户ID（逻辑关联user.id）',
  `title`         VARCHAR(100)                               NOT NULL                    COMMENT '活动标题',
  `description`   TEXT                                                                   COMMENT '活动描述（支持AI生成填充）',
  `location`      VARCHAR(255)                               DEFAULT NULL                COMMENT '活动地点（纯文本，如"人文馆主厅"）',
  `tags`          VARCHAR(255)                               DEFAULT NULL                COMMENT '活动标签JSON数组，有且仅有["文艺演出","体育赛事","学术讲座","文化活动","社团活动","心理健康"]'
  `start_time`    DATETIME                                   NOT NULL                    COMMENT '活动开始时间',
  `end_time`      DATETIME                                   DEFAULT NULL                COMMENT '活动结束时间（为NULL表示无固定结束时间，不会自动变为finished）',
  `total_tickets` INT                                        NOT NULL DEFAULT 0          COMMENT '门票总数',
  `sold_tickets`  INT                                        NOT NULL DEFAULT 0          COMMENT '已售门票数',
  `status`        ENUM('draft', 'online', 'offline', 'finished') NOT NULL DEFAULT 'draft' COMMENT '上下线状态：草稿/上线/下线/已结束',
  `created_at`    DATETIME                                   NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '发布时间',
  `updated_at`    DATETIME                                   NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '最近更新时间',
  INDEX `idx_organizer` (`organizer_id`),
  INDEX `idx_status` (`status`),
  INDEX `idx_start_time` (`start_time`),
  INDEX `idx_end_time` (`end_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='活动表';


-- ============================================
-- 表3: ticket — 门票
-- ============================================
CREATE TABLE `ticket` (
  `id`          BIGINT                                       PRIMARY KEY AUTO_INCREMENT  COMMENT '主键',
  `event_id`    BIGINT                                       NOT NULL                    COMMENT '关联活动ID（逻辑关联event.id）',
  `user_id`     BIGINT                                       NOT NULL                    COMMENT '票主用户ID（逻辑关联user.id）',
  `ticket_no`   VARCHAR(64)                                  NOT NULL UNIQUE             COMMENT '票号，生成规则: {eventId}_{userId}_{timestamp}',
  `status`      ENUM('pending', 'checked', 'invalid', 'refunded') NOT NULL DEFAULT 'pending' COMMENT '状态：待签到/已签到/已失效/已退票',
  `created_at`  DATETIME                                     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '购票时间',
  `checked_at`  DATETIME                                     DEFAULT NULL                COMMENT '核销时间（签到成功时记录）',
  UNIQUE INDEX `uk_event_user` (`event_id`, `user_id`),
  INDEX `idx_event` (`event_id`),
  INDEX `idx_user` (`user_id`),
  INDEX `idx_status` (`status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='门票表';
```
