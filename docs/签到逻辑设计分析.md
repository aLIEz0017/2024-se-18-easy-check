## 分析结果：签到时的去重与防作弊实现

在 `TicketServiceImpl.checkin()` 方法中，**去重和防作弊都有体现**，且是多层次、多角度的设计。以下是逐层分析：

---

### 1. ✅ 二维码防重放（防作弊 — 凭证时效性）

**位置：** Step 1 → Step 2（完整格式 `FULL_PATTERN`）

```java
long now = System.currentTimeMillis() / 1000;
if (now - timestamp > 60) {
    throw new BizException(4102, "二维码已过期，请刷新");
}
```

- 完整格式的签到凭证包含生成时的 Unix 时间戳
- 服务端校验该时间戳与当前时间之差是否超过 **60 秒**
- 防止二维码被截图或拍照后，在长时间内被重复使用（重放攻击）

> **注意：** 手动输入格式（`SIMPLE_PATTERN`）跳过此校验，这是合理的——手动输入场景下用户无法即时刷新凭证。

---

### 2. ✅ 格式校验（防作弊 — 凭证合法性）

**位置：** Step 1

- 两种正则表达式严格匹配凭证格式：
  - `FULL_PATTERN`：`^ticket_(\d+)_(.+)_(\d{10,})$`
  - `SIMPLE_PATTERN`：`^ticket_(\d+_\d+_\d{10,})$`
- 不匹配直接抛 `4101` 异常，拒绝非法构造的凭证

---

### 3. ✅ 活动 ID 匹配校验（防作弊 — 跨活动冒用）

**位置：** Step 3a

```java
if (parsedEventId != null && !parsedEventId.equals(ticket.getEventId())) {
    throw new BizException(4101, "无效的签到凭证，票务与活动不匹配");
}
```

- 从完整格式中解析出的 `eventId` 必须与数据库中该 ticket 所属的活动一致
- 防止持有 A 活动票的人伪造凭证去 B 活动签到

---

### 4. ✅ 举办方权限校验（防作弊 — 非授权签到）

**位置：** Step 3b

```java
if (!event.getOrganizerId().equals(userId)) {
    throw new BizException(4002, "权限不足，您不是该活动的举办方");
}
```

- 只有活动的举办方（`organizerId`）才有权执行签到操作
- 防止无关人员随意扫别人票上的码

---

### 5. ✅ 票状态机去重（去重 — 同一张票不可多次签到）

**位置：** Step 4

```java
if ("checked".equals(ticketStatus)) throw new BizException(4104, "请勿重复签到");
if ("invalid".equals(ticketStatus)) throw new BizException(4105, "票务已失效");
if ("refunded".equals(ticketStatus)) throw new BizException(4106, "票务已退票");
```

- 只有 `pending` 状态的票允许签到
- `checked`（已签到）、`invalid`（已失效）、`refunded`（已退票）均拒绝

---

### 6. ✅ 数据库原子更新防并发（去重 — 并发安全）

**位置：** Step 5 + `TicketMapper.updateCheckin()`

```java
int affected = ticketMapper.updateCheckin(ticket.getId());
if (affected == 0) throw new BizException(4104, "请勿重复签到");
```

对应的 SQL（来自 Mapper 注释）：

```sql
UPDATE ticket SET status = 'checked', checked_at = NOW()
WHERE id = #{ticketId} AND status = 'pending'
```

- **条件更新**：`WHERE status = 'pending'` 保证只有状态为 pending 的记录能被更新
- **受检行数**：如果 `affected == 0`，说明状态已被其他请求先改为 checked（并发竞争）
- 这是**最底层的原子防重屏障**，即使 Step 4 的状态校验因并发时序问题失效，此处的条件更新仍能兜住

---

### 7. 🔗 购票阶段的防重复（间接关联签到去重）

购票时（`purchase()` 方法）也做了重复购票检查：

- 逻辑层：`selectCount` 按 `eventId + userId` 查已有记录数
- 数据库层：`DataIntegrityViolationException` 捕获唯一索引冲突

这确保**一张活动 + 一个用户最多只有一张票**，从源头减少了签到重复的可能性。

---

### 总结矩阵

| 防护层次 | 机制 | 对抗什么 |
|---|---|---|
| 凭证时效性 | 时间戳 60 秒过期校验 | 二维码重放攻击 |
| 凭证格式 | 正则严格匹配 | 伪造凭证 |
| 活动匹配 | eventId 比对 | 跨活动冒用 |
| 权限校验 | organizerId 比对 | 非授权签到 |
| 状态机 | 状态前置检查（checked/invalid/refunded） | 重复签到 |
| 原子更新 | UPDATE + WHERE status='pending' + 受检行数 | 并发重复签到 |
| 购票约束 | 唯一索引 + 逻辑查重 | 一人一票（源头去重） |

**结论：** 签到模块的去重与防作弊设计较为完善，采用了**应用层逻辑校验 + 数据库条件更新**的双重保障策略，覆盖了凭证伪造、重放攻击、跨活动冒用、非授权签到、重复签到以及并发竞争等常见风险场景。
