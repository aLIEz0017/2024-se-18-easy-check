# 智能推荐引擎 — 设计实现方案

> 对应 PRD 模块三-1「活动大厅与推荐」— 【AI 禁飞区】智能推荐引擎
> 接口：`GET /api/v1/recommend/events`，返回 Top 3 活动

---

## 一、当前现状分析

### 现有代码

- `RecommendServiceImpl.java`：占位实现，按 `sold_tickets / total_tickets DESC` 排序，`userId` 参数未使用，`reason` 固定为 "热门推荐"
- `User.tags`：用户偏好标签，JSON 数组格式，如 `["科技","电竞"]`
- `Event.tags`：活动标签，JSON 数组格式（步骤 1、2 **已实现**）

### 核心问题

| 问题 | 影响 |
|------|------|
| 用户画像仅限偏好标签 + 性别 | 数据维度有限，不适合复杂推荐算法 |
| 活动总数可能较少（高校场景） | 协同过滤等算法受冷启动和数据稀疏性影响大 |
| 推荐算法未实现标签匹配 | 当前仍为纯热度排序，userId 参数未被使用 |

## 二、方案选型：手写加权排序算法

### 2.1 为什么选加权排序而非纯 AI 推荐

| 维度 | 加权排序（选用 ✅） | 纯 AI 推荐 |
|------|-------------------|-----------|
| 符合 PRD 约束 | ✅ 明确要求"手写加权排序算法" | ❌ 偏离 PRD 要求 |
| 响应延迟 | ✅ 毫秒级（纯内存 + SQL） | ❌ 1~3 秒（LLM 调用） |
| 可靠性 | ✅ 无外部依赖，不存在 LLM 不可用 | ❌ LLM API 故障时不可用 |
| 可调试性 | ✅ 权重透明，得分可追溯 | ❌ 黑盒输出，难以定位问题 |
| 无标签兜底 | ✅ 降级为纯热度排序 | ❌ 缺少特征时效果更差 |

### 2.2 AI 的定位：增强推荐理由

加权排序负责选出 Top 3 活动，AI（LLM）仅用于生成个性化的推荐理由文案——这是**可选增强层**，AI 不可用时降级为固定文案。

## 三、详细设计

### 3.1 加权评分公式

```
score = w₁ × tagMatchScore(user, event) + w₂ × sellRate(event)
```

| 变量 | 说明 | 取值范围 | 初始权重 |
|------|------|---------|---------|
| `tagMatchScore` | 用户偏好标签与活动的匹配度 | [0, 1] | w₁ = 0.6 |
| `sellRate` | 活动售票率（归一化热度） | [0, 1] | w₂ = 0.4 |

### 3.2 标签匹配度计算

#### 方案 A（推荐）：活动增加 tags 字段

给 `event` 表增加 `tags` 字段，举办方发布活动时填写活动标签（如 `["科技","讲座"]`）。

**数据库变更：**

```sql
ALTER TABLE `event` ADD COLUMN `tags` VARCHAR(255) DEFAULT NULL
    COMMENT '活动标签JSON数组，如["科技","讲座"]' AFTER `description`;
```

**匹配度计算：**

```
tagMatchScore = |userTags ∩ eventTags| / |userTags|

例：用户标签 ["科技","电竞"]，活动标签 ["科技","音乐"]
→ 交集 = {"科技"}，用户标签数 = 2
→ tagMatchScore = 1/2 = 0.5
```

**用户未设置标签时的兜底**：
- 如果 `user.tags` 为 NULL 或空数组 → `tagMatchScore = 0`，完全按热度排序

#### 方案 B（无需改表）：基于历史购买记录

如果不改表，可以通过用户历史购票活动来推算偏好：
- 查询用户已购买的活动列表
- 计算用户最常购买的活动类型（目前没有类型字段，无法实现）
- **结论：无标签字段时此方案不可行**

### 3.3 售票率归一化

```
sellRate = totalTickets > 0 ? soldTickets / totalTickets : 0.0
```

处理边界：
- `totalTickets = 0` → `sellRate = 0`（避免除零）
- 使用 `double` 计算，精确到小数点后 4 位

### 3.4 Top N 选取

- 从 `online` 状态活动中按 `score` 降序取 Top 3
- 当 `online` 活动少于 3 个时，返回实际数量（不补位）
- 当筛选结果为 0 时，返回空列表（不降级回兜底查询）

### 3.5 推荐原因说明

AI（LLM）作为可选增强层，在 `llm.enabled=true` 时介入生成个性化推荐理由；AI 不可用或失败时降级为固定文案。

| 优先级 | 情形 | reason 文案 | 说明 |
|--------|------|------------|------|
| 最高 | AI 启用 + 调用成功 + 返回非空 | AI 实时生成（如 `"根据你的【科技】偏好推荐【AI 技术沙龙】"`） | LLM 个性化文案 |
| 高 | 缓存命中 | 缓存中的历史 AI 文案 | 避免重复调 LLM |
| 中 | `tagMatchScore > 0` + AI 不可用/失败 | `"根据你的偏好标签推荐"` | 固定降级 |
| 低 | `tagMatchScore = 0` + AI 不可用/失败 | `"热门活动推荐"` | 纯热度降级 |

**AI 集成实现：**

- AiService 接口新增 `generateRecommendReason()` 方法
- MockAiService 实现模板化文案（含标签匹配 + 售票率信息）
- DeepSeekAiService 通过 Hutool HttpUtil 调用 DeepSeek API（OpenAI 兼容格式）
- RecommendPromptBuilder 独立构造推荐理由专用 Prompt
- Caffeine 本地缓存，key=`"recommend:{userId}:{eventId}"`，TTL=5min
- 配置控制：`llm.enabled`、`llm.provider`、`llm.api.*` 等通过 `application.properties` 管理

## 五、降级与异常处理

| 场景 | 行为 |
|------|------|
| 用户未登录 | 由控制器决定是否传 userId=null，此时按纯热度排序 |
| 用户无偏好标签 | tagMatchScore = 0，完全按 sellRate 排序 |
| 所有活动 tagMatchScore 均为 0 | 降级为纯热度排序（sellRate DESC） |
| 数据库查询异常 | 抛出 BizException，由全局异常处理 |
| 活动表无 online 状态记录 | 返回空列表 |

### 步骤 3 修正详情

**原描述：**「新增 `UserMapper` 中按 `userId` 查用户」

**修正：** `UserMapper` 已继承 `BaseMapper<User>`，其 `selectById(Serializable)` 方法已能按主键 `id`（即 userId）查询用户，**无需在 `UserMapper` 中新增任何方法**。真正需要做的是在 `RecommendServiceImpl` 中：

1. 注入 `UserMapper`（当前只注入了 `EventMapper`）
2. 用 `userMapper.selectById(userId)` 查询用户，获取其偏好标签（`User.tags`，JSON 字符串）
3. 解析 JSON 字符串得到 `List<String>` 用户标签列表

> **JSON 解析说明：** `EventServiceImpl` 已有 `private` 的 `parseTags()` 方法。后续实现时有两种选择：
> - 提取为公共工具类（如 `TagUtils`），让 `RecommendServiceImpl` 和 `EventServiceImpl` 共用
> - 或在 `RecommendServiceImpl` 中自行实现 JSON 解析（需注入 `ObjectMapper`）

### 步骤 4~6 实现要点

这三个步骤本质上是同一个方法的重写，合并说明：

#### 4.1 改成分页查询为全量查询

当前 `recommendEvents()` 使用 `selectPage` 做分页 SQL 查询。加权评分需要**在内存中对所有 `online` 活动计算评分后排序**，因此应改为：

```java
// 查询所有 online 活动（不使用 Page）
QueryWrapper<Event> wrapper = new QueryWrapper<>();
wrapper.eq("status", "online");
List<Event> allOnlineEvents = eventMapper.selectList(wrapper);
```

然后对全量列表计算加权评分、降序排序、取 Top N（默认 3 条），最后再包装为 `PageResponse`。

#### 4.2 加权评分逻辑

用以下公式在内存中计算每个活动的评分：

```
score = w₁ × tagMatchScore + w₂ × sellRate
```

- **`tagMatchScore`**：用户标签与活动标签的交集大小 / 用户标签总数
  - `userId == null` → 跳过标签匹配，`tagMatchScore = 0`
  - 用户无标签或空数组 → `tagMatchScore = 0`
  - 活动无标签 → `tagMatchScore = 0`
- **`sellRate`**：`soldTickets * 1.0 / totalTickets`（`totalTickets == 0` 时取 0）
- **初始权重**：`w₁ = 0.6`，`w₂ = 0.4`

#### 4.3 兜底逻辑

| 场景 | 行为 |
|------|------|
| `userId == null` | 跳过标签匹配，纯热度排序 |
| 用户偏好标签为 null 或空 | 同上 |
| 所有活动 `tagMatchScore` 均为 0 | 降级为纯 `sellRate DESC` 排序 |
| 无 `online` 活动 | 返回空列表 |

#### 4.4 推荐原因字段

```
tagMatchScore > 0 → "根据你的偏好标签推荐"
否则 → "热门活动推荐"
```

#### 4.5 处理 page/size 参数

当前 `RecommendController` 接收 `page`（默认 1）和 `size`（默认 10）。新实现应：
- 忽略 `page` 参数（始终从全部活动的评分结果中取 Top N）
- `size` 作为实际返回条数，默认取 3（与文档接口规格保持一致）

## 七、注意事项

1. **Event.tags 格式规范**：与 `User.tags` 保持一致，使用 JSON 数组字符串，如 `["科技","讲座"]`
2. **标签值枚举**：建议与 PRD 保持一致，限定在 `科技`、`电竞`、`音乐`、`学术` 四个标签，方便匹配
3. **权重的可调性**：`w₁`、`w₂` 建议定义为常量（如 `private static final double TAG_WEIGHT = 0.6`），方便后续调整
4. **性能考虑**：查询所有 `online` 活动后在内存中计算评分，适合高校场景（活动数通常在几十到几百），无需考虑海量数据
5. **userId 为 null**：控制器层可能传递 null userId（用户未登录），此时跳过标签匹配，完全按热度排序
