# 产品需求文档 (PRD)：易签 (EasySign) 活动票务与智能签到系统

## 1. 项目概述

本项目是一个面向高校/社团的活动票务与智能签到 Web 应用。项目采用“微创新”业务流，融合 AI 推荐、防并发超卖、动态二维码防作弊签到等核心技术。  
目标是为举办方提供直观的数据看板和高效率签到工具，为参会者提供个性化、流畅的购票体验。

---

## 2. 核心模块设计

### 一：全局基础模块 (用户与权限)

- **极简注册/登录**：仅需账号、密码。注册时明确选择身份（“普通参会者” 或 “活动举办方”）。

- **静态化策略**：账号一旦注册，分配固定默认头像，身份不可更改（减少鉴权复杂度）。

- **用户画像收集**：仅当注册身份选择为“普通参会者”时，首次注册成功后才进入偏好设置页，补充性别（服务于大屏数据分析）及偏好标签（如：科技、音乐、学术），提交完成后再回到登录界面。“活动举办方”注册后不进入偏好设置页，直接回到登录界面。此画像信息允许后期修改，**服务于后续的 AI 推荐算法**。

### 模块二：B端 - 举办方后台 (桌面端架构)

采用经典的 PC 端中后台布局（左侧导航 + 右侧内容）。

- **1. 数据大屏 Dashboard**
  
  - **全局视图**：展示系统级核心指标（活动在线/下线状态统计、总售票量、累计签到人数）。
  
  - **可视化图表**：ECharts 渲染各活动售票比例（饼图）、近 7 天全盘签到趋势（折线图）、参会者男女比例（饼图）。
  
  - **参会率预测展示**：在每个**未开始**的活动详情页，展示一个预测到达率（如 85%）。
    
    - 实现要求：后端有独立的 Java 类进行“特征工程”计算（提取历史同类到达率、热度等特征得出基准分），随后将基准分和特征拼接为 Prompt 传给 LLM（大语言模型），生成最终的图文建议报告。

- **2. 活动管理**
  
  - **极简发布机制**：填写活动名称、门票限额、活动简介以及活动时间，会用于其他模块的设计与实现。
  
  - **一键吸睛文案**：标题输入框旁设“AI 润色”按钮，调用大模型 API 自动扩写、美化活动简介（支持流式输出和多次重新生成）。
  
  - **上下架管理**：展示活动列表，支持一键上线/下线操作（下线后，用户侧已购门票标记为失效）。

- **3. 扫码核销（核心核销闭环）**
  
  - 提供专属核销路由页面。点击唤起 PC/手机 摄像头进行扫码。
  
  - 提供“票号输入框”作为环境受限时的兜底方案。核销成功后，大屏签到数据实时更新。

### 模块三：C端 - 参会者前台 (伪移动端视图)

**UI 架构约束**：C端所有页面强制按手机尺寸设计（宽 375px/414px）。在 PC 浏览器访问时，外层包裹 c-end-container 样式类（居中显示、带边框阴影、内部滚动），实现“PC端内置手机模拟器”的沉浸式极速开发模式。

- **1. 活动大厅与推荐**
  
  - 展示当前在线的售票活动列表。
  
  - **智能推荐**：大厅顶部独立出“为你推荐”模块。
    
    - 实现要求：后端不使用传统数据库条件筛选，而是根据用户的偏好标签和历史记录，以及活动的“综合热度（已售票/总票数）”手写加权排序算法，返回 Top 3 的活动。

- **2. 购票操作（考核点：售票并发）**
  
  - 核心操作流：点击活动 -> 立即抢票 -> 反馈抢票成功或失败（如售罄）。
  
  - **防并发超卖控制**：
    
    - 实现要求：多线程环境下，绝对不允许活动余票扣成负数。需手写并发控制逻辑。

- **3. 我的票夹（考核点：动态二维码生成）**
  
  - 状态展示：仅展示当前用户抢到的票，分为“待签到”、“已签到”、“已失效”（活动被主办方下线）。
  
  - **动态防伪二维码**：仅针对“待签到”门票生成二维码。二维码内容必须由 票号_当前时间戳 拼接而成，由前端本地库生成渲染。

### 模块四：核心业务流转 (智能签到闭环)

此模块为系统核心主干道，串联 B/C 两端。

1. **出示**：参会者在【我的票夹】展示动态二维码。

2. **扫码**：举办方在【扫码工作台】唤起摄像头对准二维码。

3. **解析**：前端扫码库解析出明文串（如：ticket_1001_1718888888），并 POST 至后端核销 API。

4. **防作弊与防重复拦截**：
   
   - **时间戳校验（防作弊）**：后端截取请求中的时间戳，与服务器当前时间对比，差值超过 60 秒则抛出异常“二维码已过期，请刷新”。
   
   - **幂等性与锁（防重复）**：并发扫描同一张截图时，利用数据库唯一约束或并发锁，确保一张票只能将状态从 待签到 更新为 已签到 一次，重复请求返回“请勿重复签到”。

5. **成功反馈**：签到成功，C 端票面状态改变，B 端大屏统计数据实时 +1。

## 3. 高级功能拓展

在稳妥完成 MVP 闭环的基础上，本系统预留了 3 个真实场景的高级功能点，作为后续项目追求的目标。

### 一：千人并发秒杀引擎

- **业务场景**：全校 3000 人在同一秒钟抢夺 100 张观影票。

- **技术升级**：引入 **Redis 中间件**。放弃直接操作 MySQL 扣减库存。

- **实现方案**：
  
  1. 预热：活动上线时，将可用库存同步至 Redis。
  
  2. 防刷：接口层引入令牌桶算法限流。
  
  3. 扣减：使用 Redis Lua 脚本保证库存扣减的原子性，实现毫秒级高并发不超卖。
  
  4. 异步落库：将抢票成功记录推入 Redis Stream，后台开启异步线程平滑写入 MySQL 数据库。

### 二：实时协同选座与防碰撞机制

- **业务场景**：活动允许用户在线选定具体座位。

- **技术升级**：引入 **WebSocket 长连接**与 **Canvas 渲染**。

- **实现方案**：
  
  1. 前端基于 Canvas/SVG 渲染二维座位矩阵，支持缩放拖拽。
  
  2. 用户 A 选中某座位的瞬间，通过 WebSocket 广播，使得系统内所有用户屏幕上的该座位瞬间标红（锁定状态）。
  
  3. 配合 Redis 分布式锁（如 Redisson）解决极小概率下的“毫秒级并发同抢一座”碰撞冲突问题。

### 三：AI Agent 深度票务管家

- **业务场景**：用户不愿在繁杂的界面中点击操作，希望通过自然语言直接完成办票。

- **技术升级**：引入 **LLM Function Calling（大模型函数调用）**。

- **实现方案**：
  
  1. 注册后端核心业务函数（如：buyTicket(eventId), searchEvent(keyword)）至大模型工具池。
  
  2. 在 C 端悬浮一个对话框，用户输入：“帮我退掉明天的讲座，改买一张今晚的人工智能沙龙门票”。
  
  3. 大模型解析意图，**自主调用后端对应的两个 API 接口**完成退票和买票操作，最后用自然语言回复用户。真正实现“可行动的 AI (Actionable AI)”。
