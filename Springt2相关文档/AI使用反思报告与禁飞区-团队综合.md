## 一、项目概况

**EasyCheck（易签）** 是一款面向高校社团的轻量化活动票务与智能签到平台，覆盖活动管理、票务并发抢购、实时协同选座、AI 智能推荐与参会率预测等场景。

### 1 技术架构

| 层 | 技术栈 | 备注 |
| --- | --- | --- |
| **前端（C 端）** | Vue 3 + Element Plus + GSAP + WebSocket | 活动大厅、详情、选座、票夹、二维码签到 |
| **前端（B 端）** | Vue 3 + Element Plus + ECharts | 活动发布/编辑、数据大屏、座位查看 |
| **后端** | Spring Boot 3 + MyBatis-Plus + MySQL | 单体架构，Maven 构建 |
| **AI 服务层** | 接口抽象 `AiService` + Mock/DeepSeek 双实现 | 依赖注入按配置切换，自动降级 |
| **实时通信** | WebSocket | 座位状态实时同步 |

## 二、AI 辅助开发的整体使用情况

### 2.1 使用的 AI 工具

全团队统一使用 **Cline（VS Code 插件）**，后端基于 Claude 能力、前端基于 GPT 系列模型。主要使用能力包括：

| 能力类型 | 具体使用 |
| --- | --- |
| 代码生成 | Controller/Service 骨架、Mapper XML、Vue 页面组件 |
| 方案设计 | 技术方案文档（并发、限流、缓存策略） |
| 文档生成 | 需求分析、架构设计、接口设计的辅助撰写 |
| 调试辅助 | 错误定位、依赖冲突排查、WebSocket 联调 |
| 代码审查 | AI 生成的代码进行人工复核 |
| 架构咨询 | 技术选型讨论、方案对比（如 Spring Security vs jBCrypt） |

### 2.2 AI 使用方式（团队共识）

团队形成了统一的 AI 协作策略，总结为三类使用模式：

**模式一：文档先行 + AI 填充（王宇航、谭逸皓）**

> 先由人给出设计约束和业务规则，AI 负责将约束扩展为完整文档和代码骨架。人审阅、修正内部矛盾后用于指导开发。

**模式二：明确边界 + 多轮收紧（谭逸皓、樊昱天）**

> 每次提问明确角色、任务范围、允许修改的目录、不可越过的边界。通过多轮小步反馈逐步接近最终效果，每轮验证构建不通过。

**模式三：防御性设计 + 降级兜底（刘逸轩、王宇航）**

> AI 生成的方案默认只有主路径，人必须补充异常处理、降级策略和边界覆盖。核心敏感功能划入禁飞区，要求人工手写。

## 三、分模块 AI 使用记录

### 3.1 认证模块（刘逸轩）

**AI 建议**：引入 `spring-boot-starter-security`，配 `SecurityConfig` + `BCryptPasswordEncoder`。

**最终决策**：拒绝 AI 方案。Spring Security 依赖过大（10+ jar）、自动开启安全过滤链需额外配置。改用 `org.mindrot:jbcrypt:0.4`（50KB）+ 手写拦截器。

**另一个陷阱**：AI 配置拦截器时用 `excludePathPatterns("/api/v1/event/*")` 放行活动详情，但未区分 HTTP 方法，导致 `PUT` 更新接口也被放行，`UserContext.getUserId()` 返回 null。修正为方法级权限过滤。

**反思**：AI 在方案选型上倾向引入大框架，需要人工压为轻量方案；路径放行策略必须考虑 HTTP 方法维度。

### 3.2 活动管理 & 票务并发（王宇航）

**AI 贡献**：
- 生成了 8 个 DTO 的字段设计和校验注解、6 个 Service 方法的实现步骤、5 条自定义 Mapper XML SQL
- 设计票务并发从"MySQL 原子 UPDATE"到"独立库存表 + 异步落库桥接模式"的递进方案
- 参会率预测算法的人机协作：AI 提供多种候选模型，人类基于业务直觉选择权重

**AI 遗漏的关键问题**：
1. **事务提交后才入队**：AI 设计的秒杀引擎中 `enqueue()` 在事务内执行，若事务回滚会产生"幽灵票"。修正为 `TransactionSynchronizationManager.afterCommit()` 确保一致性。
2. **时间字段交叉比较**：AI 生成了 startTime/endTime 跨字段校验的骨架，但只处理了"同时修改"的情况，漏掉了"只改 startTime"和"只改 endTime"两个分支。

**反思**：AI 擅长生成"看起来完整"的方案，但并发场景下的竞态条件和事务边界是最易出错的领域。AI 的方案文档容易出现前后矛盾（前半部分说必填、后半部分示例 JSON 标记为可选），需人工通读修正。

### 3.3 签到模块（刘逸轩）

**AI 翻车**：签到二维码正则表达式写了三版都是错的。

AI 未能理解 `ticketNo` 的格式是 `{eventId}_{userId}_{timestamp}`（已包含 eventId），一直在用 `ticket_{eventId}_{ticketNo}_{timestamp}` 匹配，导致 eventId 重复解析。最终手写正则一次性通过。

**反思**：AI 对项目内的字段格式约定缺乏"记忆"，反复在同一问题上犯错。核心解析逻辑必须手写。

### 3.4 前端 C 端页面（樊昱天）

**AI 贡献**：
- 6 个核心页面骨架：活动大厅、详情页、票夹、个人中心、选座组件、C 端布局
- GSAP 页面过渡动画（大厅→详情页白色展开动画）
- WebSocket 实时座位更新集成

**踩坑**：
1. AI 只关注单个 Vue 文件而忽略关联的 CSS 文件，导致样式不生效
2. `sessionStorage` 多 Tab 共享问题：同时打开两个窗口时数据互相覆盖

**反思**：给 AI 的约束需要包括具体文件范围，不能假设 AI 会自动关联相关文件。

### 3.5 前端 B 端页面（谭逸皓）

**AI 贡献**：
- 发布活动页门票数量设置组件（默认 100、范围 1-100、步进 1）
- 数据大屏近七天活动趋势图表展示
- AI 参会率预测卡片展示（四因子、分析原因、运营建议）
- 活动详情页只读座位查看（10×10 网格、A/B/C/D 四区）

**人机协作亮点**：
- 发布/编辑活动：通过多轮对话逐步修正"票务设置不可修改"为"总票数可修改但不能低于已售票数、选座设置不可改"
- 活动趋势统计：AI 先诊断数据链路，发现后端使用 `created_at` 而非 `start_time` 后说明必须改后端，人确认后才授权修改
- 座位查看：人明确要求只展示数据库真实存在的 `available` 和 `sold` 两种状态，拒绝 AI 虚构的"占座"状态

**反思**：前端成员也必须理解数据来源。AI 可以快速追踪数据链路，但业务状态必须与数据库真实字段一一对应，不能虚构。

### 3.6 DeepSeek AI 服务接入（团队协作）

**AiService 接口设计**：定义了三个核心方法——文案生成、参会率预测（废弃）、推荐理由生成。

**MockAiService**（默认实现）：占位 MVP，`@ConditionalOnProperty(name = "llm.provider", havingValue = "mock", matchIfMissing = true)`。返回模板化文案，推荐理由按标签匹配、售票率分四级降级。

**DeepSeekAiService**（真实实现）：通过 Hutool HttpClient 调用 DeepSeek API（OpenAI 兼容格式），带重试和退避策略。

**关键决策**：
- Mock 与 DeepSeek 通过 `llm.provider` 配置切换，**不删除 Mock**——API Key 未配、服务不可达、网络不通时自动降级
- 前端返回 `aiProvider` 字段，UI 显示当前使用的 Provider
- RecommendPromptBuilder 独立管理 Prompt 模板，保持"人可控"

**反思**：AI 曾建议直接删除 `MockAiService`——这在没有考虑 API 可用性风险的情况下是不可接受的。接口抽象 + 条件注入 + 自动降级是 AI 服务集成的最佳实践。

## 四、AI 能力的边界总结

| 能力维度 | AI 表现 | 人类补充 |
| --- | --- | --- |
| 结构化文档生成 | ⭐⭐⭐⭐⭐ 极高效率 | 提供领域知识和约束条件，修正内部矛盾 |
| 标准 CRUD 代码 | ⭐⭐⭐⭐⭐ 准确率 95%+ | 补全边界处理和字段约束 |
| Vue 页面骨架 | ⭐⭐⭐⭐⭐ 快速搭建 | 视觉判断、业务状态映射、CSS 细节调整 |
| 并发/事务场景 | ⭐⭐⭐ 容易遗漏竞态条件 | **必须严格审查** |
| 正则/解析逻辑 | ⭐⭐ 多次在同一点重复犯错 | 核心解析逻辑建议手写 |
| 方案选型 | ⭐⭐⭐ 倾向大框架 | 压为轻量方案（如 jBCrypt vs Spring Security） |
| 异常处理 | ⭐⭐⭐ 默认抛通用异常 | 强制使用业务异常体系 + 降级策略 |
| 注释与代码一致性 | ⭐⭐ 易被陈旧注释误导 | 人必须交叉验证 |
| 业务状态映射 | ⭐⭐ 易虚构数据库不存在的状态 | 必须与实际字段一一对应 |

## 五、AI 禁飞区

### 5.1 后端禁飞区

| 序号 | 文件 | 核心职责 | 禁飞理由 |
| --- | --- | --- | --- |
| 1 | `AiService.java` | AI 服务接口定义 | 接口契约，影响 Mock/DeepSeek 两层实现，方法签名不可由 AI 擅自增删 |
| 2 | `MockAiService.java` | AI 服务 Mock 实现 | 降级兜底逻辑，推荐理由的四级降级策略经手工调试 |
| 3 | `DeepSeekAiService.java` | DeepSeek API 调用封装 | API 调用核心，重试/退避/超时策略需人工把控 |
| 4 | `RecommendPromptBuilder.java` | 推荐理由 Prompt 构建 | Prompt 即业务逻辑文档，必须人工掌控 |
| 5 | `LlmConfig.java` | AI 配置加载 | 配置项语义需人工确认，AI 容易误解 |
| 6 | `TicketServiceImpl.java` | 票务并发核心（防超卖） | 原子 UPDATE + 异步落库的并发安全，AI 曾遗漏 afterCommit |
| 7 | `EventServiceImpl.java` | 活动状态机 + 时间字段交叉校验 | 状态流转规则复杂，AI 的边界覆盖不完整 |
| 8 | `SeatWebSocketHandler.java` | 选座 WebSocket 实时处理 | 并发连接下的座位状态一致性，涉及竞态 |

#### 5.1.1 禁飞区详解：票务并发（`TicketServiceImpl.java`）

防超卖是系统的关键技术难点，AI 在方案设计阶段给出了从"MySQL 原子 UPDATE"到"独立库存表 + 异步落库"的递进方案，但具体实施必须人工把关：

| 关注点 | AI 方案遗漏 | 人工修正 |
| --- | --- | --- |
| 事务边界 | `enqueue()` 在事务内执行，回滚产生"幽灵票" | 改为 `TransactionSynchronizationManager.afterCommit()` |
| 限流策略 | 未考虑 RateLimiter 与业务异常的交互 | 补充限流失败的业务异常码 |
| 库存一致性 | 只考虑了正常路径 | 补充库存回滚场景的补偿逻辑 |

#### 5.1.2 禁飞区详解：签到模块

签到二维码解析涉及正则表达式和 ticketNo 格式的精确匹配，AI 连续三次失败，因此整个签到逻辑的核心解析列为禁飞区。

| 关注点 | AI 错误表现 | 人工修正方向 |
| --- | --- | --- |
| 正则匹配 | 不理解 ticketNo 已包含 eventId，重复解析 | 手写匹配规则，将 ticketNo 整体提取 |
| 签到防作弊 | 未做二维码时效性校验 | 加入 timestamp 有效期判断 |
| 签到状态管理 | 只考虑了正常签到路径 | 补充重复签到、过期签到等异常处理 |

### 5.2 前端禁飞区

| 序号 | 文件 | 核心职责 | 禁飞理由 |
| --- | --- | --- | --- |
| 9 | `SeatPicker.vue` | 选座组件（区域选择 + 座位网格 + 抢票） | 选座状态（available/sold）必须与后端字段一一对应，AI 曾虚构"占座"状态 |
| 10 | `ActivityHallView.vue` | 活动大厅搜索/筛选 | 搜索防抖 + 标签筛选 + 有余票开关，交互逻辑经手动调试 |
| 11 | 二维码签到页面 | 扫码 + 60s 自动刷新 | 二维码格式定义和签到逻辑涉及后端验证，AI 容易混淆前端展示和后端解析 |
| 12 | 数据大屏（Dashboard） | 近七天活动趋势统计 | 统计口径（start_time vs created_at）必须与后端对齐，AI 曾误导使用错误字段 |
| 13 | 活动编辑页面 | totalTickets 修改 + hasSeats 只读控制 | 业务规则复杂（可改但不能低于已售票数），多轮对话才收敛到正确逻辑 |

### 5.3 禁飞区操作规范

1. **禁飞区文件的修改必须由人工主导编码**，AI 仅限提供思路参考和代码审查建议，不得在未授权的情况下主动修改。
2. **代码审查不受限制**，AI 可以阅读和分析禁飞区文件并提供改进建议。
3. **调试辅助不受限制**，AI 可以帮助诊断禁飞区文件中的错误，但修复代码需人工确认后执行。
4. **禁飞区范围内不引入新的 AI 生成代码**，已有代码的维护、重构必须由人工完成，AI 最多提供"伪代码"级别的参考。

## 六、关键经验总结

### 6.1 正向经验

1. **AI 在文档生成方面效率最高**。15 份设计文档（约 3 万字）从 PRD 的一句话需求扩展到完整实施方案，AI 将 2-3 天的人工工作缩短到 1 小时内。

2. **接口抽象 + 条件注入 + 自动降级**是 AI 服务集成的最佳实践。MockAiService 即为默认实现，DeepSeek 不可用时系统不崩溃。

3. **多轮小步迭代优于一次性生成**。活动编辑页面从"全部禁用"到"总票数可改、选座不可改"的正确逻辑，经历了三轮人机对话才收敛。

4. **"以代码为准"原则**：Prompt 中明确要求"以代码为准，注释仅供参考"，避免 AI 被过时注释误导。

### 6.2 反面教训

1. **AI 对项目约定的"记忆力"有限**。正则表达式三版都错、拦截器路径放行不分 HTTP 方法——AI 记不住分散在多份文档中的约束条件。

2. **AI 倾向于引入大框架**。Spring Security（10+ jar）vs jBCrypt（50KB），AI 默认推荐重方案。

3. **AI 会虚构数据库不存在的业务状态**。座位查看组件中，数据库只有 `available` 和 `sold`，AI 却生成了"占座"状态。

4. **AI 容易忽略项目的异常处理约定**。多次生成 `throw new RuntimeException(e)`，绕过全局异常拦截器和 `BusinessException` 错误码体系。

5. **文档与代码漂移**。设计文档初稿有 AI 参与，实现推进后未及时更新状态，导致文档与实际代码不一致。

### 6.3 团队协作模式

AI 的有效角色是"加速器"而非"替代者"：

```
人类：业务洞察 + 决策方向 + 边界审查 + 最终判断
AI：结构化生成 + 方案推演 + 代码骨架 + 重复劳动
```

团队总结的最有效协作模式：**"人类想清楚'做什么'和'为什么'，AI 高效完成'怎么做'的落地"**。

## 七、后续改进计划

1. **AI 使用规范文档化**：将本报告的禁飞区写入 `.clinerules` 或项目规范文件，让 AI 在启动时自动加载约束。

4. **定期文档-代码对账**：每个 Sprint 结束强制"文档-代码对账"，设计文档只维护一份真相，清理过时注释。

5. **团队知识共享**：将本次 Sprint 中的 AI 翻车案例（正则三版失败、afterCommit 遗漏、SessionStorage 多 Tab）整理为团队 Wiki，避免重复踩坑。

## 八、总结（口述要点）

> EasyCheck 项目全程将 AI 定位为"加速器"而非"替代理解的黑盒"。AI 在文档生成、代码骨架、方案推演方面极大提升了效率，但核心业务逻辑（秒杀并发、签到正则、选座状态映射、活动状态机）全部由人工主导编码。
>
> 团队从本次 Sprint 中总结出三条关键经验：一是**接口抽象 + 自动降级**是 AI 服务集成的必选模式；二是**多轮小步迭代**比一次性生成更适合复杂业务逻辑；三是**禁飞区**是保护核心代码质量的必要机制。
>
> 后续将把禁飞区写进 CI/CD 审查规范，为每个禁飞区文件建立变更告警，确保团队成员在任何修改前都明确知道这是"需要人工主导"的区域。
