# AI 使用反思报告

> 项目：易签 (EasySign) 活动票务与智能签到系统  
> 个人分工：后端开发 — 活动管理 + 票务并发 + 智能推荐  
> 报告时间：2026-07-15

---

## 一、工作范围概述

我负责的后端模块包括：**活动管理（EventController/EventService）**、**票务并发（TicketController/TicketService）** 和 **智能推荐（RecommendController/RecommendService）**，覆盖约 18 个核心文件（3 个 Controller、6 个 Service/Impl、8 个 DTO 及 Mapper XML）。在整个开发过程中，AI（Claude Code）贯穿了从需求梳理、方案设计到代码实现的全部环节。

---

## 二、AI 参与全流程分析

### 2.1 需求分析与方案设计

**输入**：产品需求文档 PRD（约 3000 字，描述业务目标和核心模块）  
**产出**：15 份实施计划/设计文档，累计约 3 万字

AI 在文档生产阶段发挥了最高效率。以 `docs/活动票务推荐模块实施计划.md` 为例，AI 将 PRD 中的一句话需求（"活动 CRUD + 智能推荐"）拆解为：

- 8 个 DTO 的字段设计和校验注解
- 6 个 Service 方法的完整实现步骤
- 5 条自定义 Mapper XML 的 SQL 语句
- 实施顺序建议和风险说明

这一过程从人工完成可能需要 2-3 天的"方案文档"缩减到 1 小时内即可获得完整框架。

**关键反思**：AI 的方案产出质量高度依赖于**输入的完整性**。初期我未提供 `end_time` 字段需求和 `finished` 状态流转规则时，AI 生成的状态机遗漏了"活动自动结束"这一关键场景。补充输入后，AI 能在已有框架上快速修正——这说明**人机协作的最佳模式是"人类提供完整上下文，AI 负责结构化和填充"**。

不过，AI 在生成长篇幅设计文档时还容易出现前后矛盾的问题。例如在活动推荐实施文档中，曾出现前半部分描述某个 DTO 字段为"必填"，后半部分的示例 JSON 里却将其标记为可选；或是一处写着"采用悲观锁"，另一处又说"乐观锁兜底"。这类矛盾在人工审阅后才能发现，说明 AI 在保持长文本的**逻辑一致性**方面仍有明显短板。这也提醒我：AI 产出的设计文档不能直接照搬，必须通读并修正内部矛盾后再用于指导开发。

### 2.2 核心业务代码实现

#### 活动管理模块

活动管理的核心难度在于**状态机校验和跨字段校验逻辑**。以下展示 `updateEvent` 中 startTime/endTime 的跨字段比较逻辑，这是 AI 辅助下完成的典型复杂校验：

```java
// EventServiceImpl.updateEvent()
// 跨字段比较逻辑：同时修改 startTime 和 endTime 时比较新值，
// 只改其一则比较新值与现有值
LocalDateTime newStartTime = event.getStartTime();
LocalDateTime newEndTime = event.getEndTime();

if (req.getStartTime() != null) {
    newStartTime = parseDateTime(req.getStartTime());
    validateStartTime(newStartTime);
}
if (req.getEndTime() != null) {
    newEndTime = parseDateTime(req.getEndTime());
}
validateEndTime(newStartTime, newEndTime);
```

AI 生成了上述代码的核心骨架，但**三个时间比较场景的边界覆盖是由我补全的**。AI 最初只处理了"同时修改"的情况，我补充了"只修改 startTime"和"只修改 endTime"两个分支的判断逻辑。

#### 票务并发模块

防超卖是系统的关键技术难点。AI 给出了从基础方案到优化方案的递进设计：

**方案一（基线）**：MySQL 原子 UPDATE
```sql
UPDATE event SET sold_tickets = sold_tickets + 1 
WHERE id = #{eventId} AND sold_tickets < total_tickets
```
这是数据库层最简单的乐观锁实现，通过 WHERE 条件确保不超卖，通过行锁保证原子性。

**方案二（优化）**：独立库存表 + 异步落库
```
限流（Guava RateLimiter） → 库存独立表原子扣减 → 内存队列 → 批量写入 ticket 表
```

AI 对方案二的完整设计文档（`docs/秒杀引擎MySQL优化方案.md`）包含了四个优化层面：接口层限流、数据层库存独立、应用层队列缓冲、最终一致性保障。但 AI 最初忽略了**事务提交后才入队**这一关键问题——如果 `enqueue()` 在事务内执行而事务回滚，会产生"幽灵票"。这个 bug 是我在代码审查中发现的，修正为通过 `TransactionSynchronizationManager.afterCommit()` 确保一致。

**反思**：AI 擅长生成"看起来完整"的方案，但**并发场景下的竞态条件和事务边界**是 AI 最容易出错的领域。人类的核心价值在于发现这些"在理想条件下不会发生，但高并发下一定会出现"的边界问题。

#### 智能推荐模块

推荐模块实现了标签匹配度 + 售票率的双重加权排序：

```java
// 核心公式
double score = TAG_WEIGHT * tagMatchScore + HEAT_WEIGHT * sellRate;

// 标签匹配度计算：交集大小 / 用户标签总数
// tagMatchScore = |userTags ∩ eventTags| / |userTags|
// 售票率 = soldTickets / totalTickets
```

AI 实现了完整的排序算法和推荐理由生成。其中推荐理由部分设计了**三级降级策略**：
1. AI 实时生成个性化文案（LLM 可用时）
2. 标签匹配固定文案（LLM 不可用时）
3. 纯热度降级文案（无标签匹配时）

这种防御性设计是多轮对话中逐渐形成的，体现了 AI 在**方案演进**中的价值——每次补充约束条件，AI 都能在不破坏现有结构的前提下增量调整。

### 2.3 关键算法的人机协作过程

参会率预测算法的设计过程最能体现人机协作的真实互动（详细记录见 `docs/算法设计文档.md`）：

| 轮次 | AI 的作用 | 人类的作用 | 协作结果 |
|------|-----------|-----------|----------|
| 第一轮 | 提出三因子模型（历史签到率+距离系数+热度） | 指出"距离系数在同一时间点对所有活动无区分度" | 排除距离系数 |
| 第二轮 | 简化两因子模型，被动等待新需求 | "有没有其他可能的影响因素？" | 扩展为四因子 |
| 第三轮 | 列出候选特征（周末因子、时段因子等） | "购票时间分布能否反映用户意愿强度？" | 提出购票集中度创新特征 |
| 第四轮 | 给出三种"购票集中度"实现方案（标准差/峰度/最后3天占比） | "一天应该分时段考虑，甲时段购票和丁时段购票含义不同" | 甲乙丙丁四时段分别计算 |

最终公式：
```
预测率 = 历史签到率 × 0.50 + 热度 × 0.20 + 购票集中度 × 0.20 + 时段因子 × 0.10
```

**这个过程的典型模式**：AI 提出结构和多种选项 → 人类基于业务直觉进行选择或批判 → AI 根据反馈细化实现 → 循环至满意。AI 在这里的角色更像一个"资深工程师助理"——能快速提供多种可行方案，但**最终的选择和方向把控必须由人类完成**。

## 三、AI 能力的边界

| 能力维度 | AI 表现 | 人类补充 |
|----------|---------|----------|
| 结构化文档生成 | ⭐⭐⭐⭐⭐ 极高效率 | 提供领域知识和约束条件 |
| 标准 CRUD 代码 | ⭐⭐⭐⭐⭐ 准确率 95%+ | 补全边界处理 |
| 并发/事务场景 | ⭐⭐⭐ 容易遗漏竞态条件 | **必须严格审查** |
| 业务创新建议 | ⭐⭐⭐ 能列举可选方案 | 选择方向、做价值判断 |
| 测试用例覆盖 | ⭐⭐⭐⭐ 覆盖主要路径 | 补充异常场景 |
| 代码风格一致性 | ⭐⭐⭐⭐⭐ 统一 | 基本无需调整 |
| 接口约定遵循 | ⭐⭐⭐ 容易忽略非功能约束 | 补充字段长度、边界值等约定 |
| 异常处理规范遵循 | ⭐⭐⭐ 倾向抛出通用异常 | 强制使用业务异常体系 |
| 注释与代码一致性判断 | ⭐⭐ 易被陈旧注释误导 | 必须交叉验证注释与实际代码 |

**总结**：AI 在"结构化、重复性、有明确规范"的工作中效率极高（文档生成、CRUD 代码、单元测试框架），但在"需要业务直觉、边界敏感、涉及一致性问题"的领域需要人类严格把关。

## 四、对 AI 协作的反思

1. **输入质量决定输出质量**：To AI 的问题越具体、上下文越完整，产出质量越高。最差的协作方式是"帮我实现一个功能"——这往往导致 AI 做出不符合项目约束的设计决策。

2. **增量迭代优于一次性生成**：在算法设计等复杂任务中，分轮次推进（先定框架→再选方案→最后实现）比要求 AI 一次给出最终方案效果更好。因为每轮的人类反馈都是在补充 AI 缺少的**业务上下文**。

3. **文档即架构**：项目积累的 15 份设计文档不仅用于记录，更成为后续与 AI 协作的"共享上下文"。当需要新增功能时，AI 能基于这些文档理解项目约束，避免做出与现有设计冲突的建议。

4. **审查是必要环节**：AI 生成的代码在语法和结构上几乎无问题，但在**并发安全、事务边界、异常处理策略**等方面需要人类审查。例如 afterCommit 回调的幽灵票问题、签到正则的边界覆盖等，都是代码审查中发现的——这些是 AI 无法"意识"到的隐患。

5. **接口约定的隐性约束需要反复确认**：AI 在实现接口时容易忽略字段长度、枚举取值等非功能性约定。例如在一些场景中，AI 生成的字段值超出了前端约定的最大长度，导致前端展示截断。这类问题源于 AI 没有"记住"分散在多份文档中的约束条件——它看到了当前接口的字段定义，却没有关联到另一份文档中的规格说明。后续做法是将所有接口约束汇总到一份 Prompt 上下文中，或通过代码审查时逐一核对。

6. **注释比代码更容易误导 AI**：有一次我在某个方法上留下了过时的注释（描述的是旧逻辑），AI 在生成新代码时只读了注释而没有仔细读方法体内的实际代码，结果新代码基于错误的假设，与现有行为冲突。这暴露出 AI 对注释和代码的**优先级判断**存在偏差——注释是"人说的"，代码是"实际做的"，AI 倾向于信任自然语言描述而非实际代码实现。此后我会在 Prompt 中明确要求"以代码为准，注释仅供参考"。

7. **异常处理最暴露 AI 的"默认偏好"**：项目约定统一使用 `BusinessException` 携带错误码和上下文信息，但 AI 在多个生成场景中直接抛出 `RuntimeException`，甚至在 catch 块中无脑 `throw new RuntimeException(e)`。这不仅绕过了全局异常拦截器的统一处理，还丢失了错误码信息，给前端排查问题带来困难。这说明**项目级约定**（尤其是"不要做什么"这类负面约束）在 AI 的上下文中极易被忽略，需要在 Prompt 中反复强调，或通过代码审查工具自动化拦截。

## 五、总结

本次开发中，AI 的角色是**高效的编码助手和方案推演工具**，而非替代者。人的核心贡献在于：

- 提供业务洞察和决策方向（如购票集中度特征、签到防作弊体系设计）
- 发现并发场景下的潜在 bug（如 afterCommit 遗漏）
- 把控系统架构的一致性和可扩展性（如状态机规则、接口设计规范）

最有效的协作模式是：**人类想清楚"做什么"和"为什么"，AI 高效完成"怎么做"的落地**。这个模式在 MVP 开发中显著提升了效率，但人类在关键决策和边界问题上的判断仍然不可替代。
