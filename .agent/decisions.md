# 架构决策记录 (Architecture Decision Records)

> 本文档记录本系统开发过程中的关键架构取舍和设计决策，便于后期维护时理解当初的考量。

---

## ADR-001：前端采用"一库双端"而非双项目

**状态**：✅ 已采纳

**背景**：系统需要同时支持 B端（举办方桌面后台）和 C端（参会者移动前台），有两种方案：拆分为两个前端项目，或在一个项目内通过路由隔离。

**决策**：在一个 Vue3 项目内，通过 Vue Router 角色鉴权实现双端隔离。

**理由**：
- 两端共享大量公共代码（API 封装、Pinia store、工具函数）
- 减少构建和部署的复杂度（一个 dist 目录，一个 Nginx 配置）
- 12 天 MVP 不需要拆分项目增加维护成本

**代价**：
- 前端构建产物包含两端代码，包体积略大（但本项目业务较轻，可接受）
- 如果未来两端差异过大，可能需要拆分

## ADR-002：C端采用"手机模拟器"而非真响应式

**状态**：✅ 已采纳

**背景**：C端需要在 PC 和手机上都能访问。有两种方案：CSS 媒体查询做真正的响应式布局，或固定宽度 + 居中容器模拟手机。

**决策**：固定宽度 400px + `.c-end-container` 容器居中，配合 `@media (max-width: 420px)` 在手机上铺满全屏。

**理由**：
- 只按一套尺寸（375px-414px）开发，节省大量适配时间
- 学校项目验收通常在 PC 上演示，居中容器视觉效果专业
- 真响应式（侧边栏折叠、导航重排等）开发工作量翻倍

**代价**：
- PC 大屏上两侧有留白，空间利用率低
- 某些 PC 原生交互（hover 效果、右键菜单）无法自然使用

## ADR-003：后端采用七层架构而非标准 MVC 四层

**状态**：✅ 已采纳

**背景**：技术栈约定中只提了 controller/service/mapper/entity 四层。经过分析，安全性和可维护性存在缺口。

**决策**：在四层基础上增补 `config/`、`common/`、`dto/` 三层，形成七层架构。

**理由**：
- **安全**：entity 直接序列化给前端会暴露敏感字段（如 password），通过 DTO 隔离
- **统一性**：common 层的 `Result<T>` 和 `GlobalExceptionHandler` 保证所有接口返回格式一致
- **可维护**：config 集中管理 CORS/拦截器/序列化等横切关注点

**代价**：
- 每个接口多一个 DTO 类（但按需创建，非强制）
- 团队需要理解七层各自的职责边界

## ADR-004：数据库不建物理外键，纯逻辑关联

**状态**：✅ 已采纳（来自 conventions.md）

**背景**：MyBatis-Plus 不推荐物理外键，MySQL 使用外键会有性能开销。

**决策**：表间关联仅通过代码逻辑保证，数据库层面不定义 FOREIGN KEY。

**理由**：
- MyBatis-Plus 的实体映射天然不需要物理外键
- 物理外键在插入/更新时会产生额外的锁和约束检查，影响写入性能
- 删除数据时不受外键约束阻塞（但需代码级保证引用完整性）

**代价**：
- 数据库层面没有引用完整性保护，脏数据需要应用层拦截
- 需要开发者自觉维护关联字段的一致性

## ADR-005：防超卖采用数据库乐观锁，而非 ReentrantLock 或 Redis

**状态**：✅ 已采纳

**背景**：抢票场景需要防止并发超卖。

**决策**：使用 `UPDATE event SET sold_tickets = sold_tickets + 1 WHERE id = ? AND sold_tickets < total_tickets` 这一原子 SQL 进行控制。

**理由**：
- Redis 被约定排除（12 天 MVP 不引入复杂中间件）
- ReentrantLock 只在单机有效，多实例部署时会失效
- MySQL 的行锁 + 条件更新本身就是数据库层面的乐观锁，简单可靠

**代价**：
- 高并发下（同一活动数千人同时抢），数据库行锁可能成为瓶颈
- 但高校/社团场景下并发量远达不到此阈值，可接受

## ADR-006：举办方的 gender/tags 字段存 NULL 而非拆分表

**状态**：✅ 已采纳

**背景**：`gender` 和 `tags` 字段仅参会者需要，举办方用不到。

**决策**：保留单表设计，举办方这两个字段存 NULL。

**理由**：
- 12 天 MVP，简单性优先
- NULL 在 MySQL 中存储开销极低（约 1 bit）
- 避免多一张表的 JOIN 开销和代码复杂度

**代价**：
- 语义上不够清晰（举办方字段虽然为 NULL 但仍存在于表中）
- 如果未来参会者字段大幅增加，可能需要拆表重构

## ADR-007：统一认证采用 JWT 而非 Session

**状态**：✅ 已采纳

**背景**：前后端分离架构需要选择认证方案。

**决策**：使用 JWT Token，登录后由后端签发，前端存储在 localStorage，每次请求通过 Authorization 头携带。

**理由**：
- 无状态，后端不需要 Session 存储
- 跨域友好（前后端可能部署在不同域名或端口）
- 前端可解析 Token 获取用户角色信息，便于路由鉴权

**代价**：
- JWT 无法主动失效（无法强制下线），但本项目不需要此能力
- Token 体积比 Session ID 大（包含 payload），但影响可忽略

## ADR-008：不设立独立的 CheckInLog 签到日志表

**状态**：✅ 已采纳

**背景**：核销签到环节是否需要独立的日志审计表。

**决策**：不建日志表，ticket 表自身的 `status` + `checked_at` 字段足以记录签到状态。

**理由**：
- 一张票在整个生命周期中最多只核销一次（防重复签到），不存在多行日志需求
- 符合极简原则，避免过度设计

**代价**：
- 无法追溯"谁在什么时间对某张票做了核销操作"（操作人审计）
- 但本项目扫码核销只有举办方操作，操作人唯一，无需审计

## ADR-009：ticket_no 票号采用 eventId_userId_timestamp 拼接格式

**状态**：✅ 已采纳

**背景**：需要一种既保证唯一性又有可读性的票号生成方案。

**决策**：票号格式为 `${eventId}_${userId}_${timestamp}`，后端在购票成功时生成。

**理由**：
- 相对自增 ID：不暴露系统总量信息，且可反解出上下文信息
- 相对 UUID：长度更短（UUID 36 字符，本方案约 20-30 字符），索引性能更好
- 可用于排查问题：拿到一个票号即可知道是哪个活动的哪个用户在什么时间购买的

**代价**：
- 极端情况下（同一用户在同一毫秒购买同一活动的票）可能冲突，但概率极低
- 如果未来需要分布式全局唯一 ID，可能需要引入 Snowflake 算法

## ADR-010：一人一票设计，暂不支持一人买多张

**状态**：✅ 已采纳

**背景**：购票策略选择。

**决策**：一个用户对同一场活动只能购买一张票，后端通过 `user_id + event_id` 唯一性检查保证。

**理由**：
- 需求文档中没有明确要求代买或批量购买
- 一人一票的逻辑最简单，不需要引入订单（order）表
- 高校/社团活动场景下，一人一票是合理的

**代价**：
- 如果未来需要支持"帮朋友买票"，需要引入 order 表做较大重构（详见 ADR 扩展性分析）

## ADR-011：不实现本阶段暂不考虑的功能

**状态**：✅ 已采纳

**背景**：需求文档明确列出多项"暂不考虑"的内容。

**决策**：以下功能在 MVP 阶段不做实现：
- 文件上传（头像、活动宣传图）
- 支付逻辑（默认免费）
- 退票/候补逻辑
- 活动结束时间和核销时间合理性判定
- 富文本编辑器和地图定位

**理由**：
- 严格控制 12 天 MVP 的开发范围
- 数据库表设计已为上述功能预留了扩展空间（详见 `docs/数据库表设计.md` 第四章）
- 不做这些逻辑意味着砍掉了大量边界情况处理，大幅降低开发工作量

**代价**：
- 产品功能完整度有限，但符合 MVP 交付预期

## ADR-012：签到接口使用业务码而非 HTTP 状态码区分错误

**状态**：✅ 已采纳

**背景**：签到接口面临多种业务错误场景（外部非法二维码、二维码过期、重复签到、票务不存在等），需要设计错误码体系。

**决策**：所有签到相关的业务错误统一返回 HTTP 200，通过响应体中的 `code` 字段（4100-4106 系列业务码）区分具体错误类型。同时将通用业务错误码规范为 4xxx 体系。

**理由**：
- 前端可统一通过 `result.code === 200` 判断成功，其余值均为异常，用 `result.msg` 展示给用户，无需对 HTTP 状态码做分支处理。
- HTTP 状态码更适合表示协议层面的语义（如 404 表示 URL 路径错误，而非"票务不存在"这一业务语义）。
- 外部非法二维码/文本格式不匹配属于业务校验异常，在 HTTP 200 下以业务码 4101 返回，语义更准确。

**代价**：
- 前端在所有接口处仍需判断 `result.code` 而非仅依赖 HTTP 状态码。
- 业务码需要前后端双方维护一套码表。

## ADR-013：Dashboard 采用"半聚合 Hybrid"策略而非全量单接口

**状态**：✅ 已采纳

**背景**：Dashboard 数据大屏需要展示核心指标（上下线状态、总售票量、累计签到）和多个图表（售票比例饼图、近7天签到趋势折线图、男女比例饼图）。有两种方案：一次请求全量聚合所有数据，或每个图表独立请求。

**决策**：采用半聚合 Hybrid 策略——核心指标作为固定字段直接返回，图表数据通过 `charts` Map 结构包裹，key 为图表标识，value 包含 `type` 和 `data`。

**理由**：
- 一个请求即可完成所有数据加载，避免前端发 3-4 个请求分别拉数据。
- `charts` 为 Map 结构，后续新增图表时只需在 `charts` 下新增 key，不破坏已有结构，扩展性好。
- 核心指标（totalSoldTickets 等）单独暴露，方便前端快速展示，无需从图表数据中反推。
- 如果未来某个图表数据量过大，可拆为独立接口按需加载，不影响 overview 基础结构。

**代价**：
- 即使前端只需要核心指标（如仅展示卡片），也会同时拉取图表数据，存在少量数据冗余。
